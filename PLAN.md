# URnetwork Linux App — Port Plan

Port of the URnetwork desktop client to a native Ubuntu 22.04 LTS / 24.04 LTS
app (GNOME/Wayland, amd64 + arm64) at `linux/app`, distributed via the **Snap
Store**. Unlike macOS/Windows (privileged daemon + RPC split), Linux uses the
**single-process, shared-memory model like Android**: one process runs the SDK's
`DeviceLocal` in-process and pumps packets through a `/dev/net/tun` fd via the
SDK's existing `IoLoop` — no RPC, no wintun, no separate service. It keeps the
macOS-style menu-bar/tray desktop UX.

Stack decisions marked **[verified]** come from a cited deep-research pass
(2026-07-09; primary sources: GNOME/GTK repos, packages.ubuntu.com, snapcraft
docs, snapd source, Mullvad/Tailscale/Proton). **[judgment]** = engineering
recommendation. **[unverified]** = the research found no surviving evidence —
these are the load-bearing follow-ups.

> **Implementation status (2026-07-10):** the app is written under `linux/app/`
> (see `linux/app/README.md`). The **core is verified**: `internal/vpn` (Host +
> auth + tun + IoLoop wiring) and `cmd/urnetworkd` (headless M0 runner)
> cross-compile for linux/amd64 + linux/arm64 against the real Go SDK API — this
> is the Android-like data plane proven to compile on Linux with **zero SDK
> changes** (`IoLoop` is already `!windows`). The GTK4 UI (`internal/ui`, gotk4),
> SNI tray (`internal/tray`), snapcraft.yaml, .desktop, and icons (from the macOS
> art) are written but need the GTK4 toolchain to compile (the on-device
> iteration surface, R1/R2). All uncommitted.
>
> **v1 scope (revised 2026-07-10): FULL macOS parity — sign in, sign up, connect
> (all controls), and provide.** The data-plane core is verified; the GTK UI
> written so far is a *minimal* slice. Full v1 adds: sign up, Google + Apple
> browser SSO, the location/provider picker, the connect detail sheets, the full
> provide surface, and the Account/Wallet/Leaderboard/Support breadth. See M2/M3.
>
> **UI language changed 2026-07-10: C++ (gtkmm4 + libadwaita), NOT gotk4/Go** —
> gotk4's memory-leak/maintenance risk (R1) outweighed its no-C-boundary benefit,
> especially since the cgo `urnetwork_sdk.hpp` wrapper already exists and lets the
> C++ app share SDK-host logic with the WinUI Windows app. The Go core written so
> far (`internal/vpn` + `cmd/urnetworkd`) is retired to a diagnostic; the shipping
> app is C++ consuming the cgo `.so`. See §2.

## 1. Architecture (single process — the Android model, not macOS/Windows)

```
+---------------------------------------------------------------+
| urnetwork (single process, in a strict snap w/ network-control)|
|                                                                |
|  GTK4 + libadwaita UI (Go, gotk4)  — macOS-style tray + window |
|        |  direct Go calls (no C ABI, no RPC)                   |
|  sdk package (imported directly):                              |
|     NetworkSpaceManager -> NetworkSpace -> Api / LocalState    |
|     DeviceLocal (NewDeviceLocalWithDefaults)                   |
|     ConnectViewController, ...                                 |
|        |  in-process fd loop                                   |
|  sdk.IoLoop(deviceLocal, tunFd)  <-->  /dev/net/tun            |
|        |  CAP_NET_ADMIN (granted to THIS process by the snap)  |
|  routes (ip rule / 0.0.0.0/1+128.0.0.0/1) + DNS (resolved)     |
+---------------------------------------------------------------+
```

Because the SDK is Go and the app is Go, `DeviceLocal` is a **direct package
import** — no c-shared library, no C ABI, no `urnetwork_sdk.hpp`, no
DeviceRemote/RPC. The app *is* the VPN, exactly like Android's `VpnService`
holding the tun fd. The SDK's `IoLoop` (`//go:build !windows`, already used on
Android) is the fd pump — it already compiles for Linux (verified: the sdk
package builds for `linux/amd64`).

**The crux that makes single-process viable inside a strict snap** [verified]:
the snap `network-control` interface grants the confined process `/dev/net/tun`
rw, `CAP_NET_ADMIN`, and netns access (per snapd `network_control.go`). So the
GUI process itself opens the tun and configures the tunnel — no privileged
helper daemon. Every commercial Linux VPN studied (Mullvad, Tailscale) instead
uses a root daemon + RPC-over-UDS, so this design is unconventional on Linux
desktop but is specifically enabled by snap network-control.

## 2. Stack decisions

- **UI: GTK4 + libadwaita in C++ (gtkmm4 + libadwaita C API), via the cgo
  `urnetwork_sdk.hpp` wrapper.** [DECIDED 2026-07-10 — was gotk4/Go]
  Rationale: gotk4 (the earlier pick) is single-maintainer, autogenerated, and
  its own README warns of memory leaks/crashes — a real liability for a multi-day
  tray/VPN process (this was R1). Its only advantage was "no C boundary," but the
  cgo C++ wrapper already exists and is verified (the Windows app uses it; it
  exposes the unix-only `IoLoop` for the fd data plane), so that advantage is
  moot. GTK4 + gtkmm-4.0 is battle-tested official GNOME (Ubuntu 22.04 ships
  gtkmm 4.6, 24.04 ships 4.14, both arches). **Bonus:** the C++ app consumes the
  SAME wrapper as the WinUI Windows app, so the SDK-facing host logic (auth,
  connect, provide control) is **shared C++ across Windows and Linux** — only the
  UI toolkit and the tun/network layer differ per platform.
  - **libadwaita from C++**: gtkmm wraps GTK4; the libadwaita C++ bindings
    (libadwaitamm) are young, so use gtkmm4 for GTK and call the libadwaita **C
    API** (`adw_*`) directly for Adw widgets (mixing gtkmm + C GObject is fine).
    22.04 ships libadwaita 1.1, 24.04 1.5 — target 1.5 and ship it in the snap
    (core24), which makes bundling practical.
  - **Cost:** the app can only be built on a Linux box with the GTK toolchain
    (no macOS cross-verify, same as the Windows C++ app); the tun + IoLoop data
    plane is already proven (container test) and calls the same IoLoop via the
    wrapper, so that confidence carries over. The earlier verified Go core
    (`internal/vpn` + `cmd/urnetworkd`) is retired to a diagnostic/test harness.
- **Tray/status: StatusNotifierItem (SNI/AppIndicator) via the Canonical GNOME
  Shell extension.** [verified] GNOME removed the legacy XEmbed systray; SNI is
  the D-Bus successor, works under Wayland, and is what Proton/Mullvad/Nord use.
  The `gnome-shell-extension-appindicator` is **preinstalled on Ubuntu** (a
  refuted claim wrongly said it needs manual install — on Ubuntu it's default).
  Emit an SNI item from Go (a Go SNI/AppIndicator lib, or dbus directly) for the
  4-state menu-bar icon + menu. **Risk R2**: on non-Ubuntu vanilla GNOME the
  extension isn't default; a manual enable needs logout/login (Wayland can't
  hot-restart the shell). Ubuntu (our target) is covered.
- **Data plane: in-process `/dev/net/tun` + SDK `IoLoop`.** [verified privilege]
  The app opens `/dev/net/tun` (granted by snap network-control), creates the
  tun interface, and hands the fd to `sdk.NewIoLoop(deviceLocal, fd)`. Same fd
  path as Android; reuses the SDK unchanged. Userspace-networking (gVisor, no
  kernel tun) exists as a fallback but is proxy-only, not a system data plane —
  kernel tun via network-control is the right path.
- **Packaging: strict-confinement Snap, `network-control` interface, core24
  base (24.04) + core22 (22.04).** [verified feasible] Proton VPN is a snap
  precedent. Build the Go(+cgo for gotk4) app with the snapcraft `go` plugin,
  amd64+arm64. **Risk R3**: `network-control` does **not** auto-connect — a
  strict VPN snap needs a manual `snap connect` or a **store-granted auto-connect
  exception** (brand/store review). Request the exception at submission.
- **Privilege outside snap (deb fallback):** [judgment] not v1. If a `.deb` is
  ever needed, the single-process model needs `setcap cap_net_admin+ep` on the
  binary or a tiny setuid/systemd fd-broker (SCM_RIGHTS) — reintroducing a
  helper. Snap-first avoids this entirely.

## 3. Component mapping

| macOS / Android | Linux |
|---|---|
| `MenuBarExtra` + 4 icons | SNI/AppIndicator tray, 4 state icons (reuse the generated art) |
| Main window (Connect/Account/Leaderboard/Support) | libadwaita `AdwApplicationWindow` + `AdwViewSwitcher` |
| `DeviceManager` → NetworkSpace/Api/LocalState + **DeviceRemote** | same, but **DeviceLocal in-process** (no remote); direct Go calls |
| macOS extension `PacketTunnelProvider` / Android `IoLoop` | `sdk.NewIoLoop(deviceLocal, tunFd)` in the same process |
| `VPNManager`/`NETunnelProviderManager` (start/stop) | in-process: open tun, `IoLoop`, set routes/DNS directly |
| Windows `urnetworkd` service + RPC | **none** — single process |
| Auth (email/pw/verify, guest, code; Google browser) | same, via `Api` directly; `urnetwork://` OAuth via xdg-desktop-portal |
| StoreKit / Stripe | Stripe checkout via `xdg-open` browser |
| Storage (per-process dir) | `$SNAP_USER_DATA` (or `$XDG_DATA_HOME/urnetwork`) → NetworkSpaceManager |
| Logs | `$SNAP_USER_COMMON/logs` → `sdk.SetLogDir` |
| Split tunnel (Win driver / Android per-app) | cgroup v2 + SO_MARK/nftables (R6, unverified in snap) |
| Notifications | `xdg-desktop-portal` Notification / libnotify |
| Launch at login | XDG autostart `.desktop` or systemd user service |

## 4. Milestones

- **M0 — headless single-process tunnel.** Go program: import sdk, build
  NetworkSpace, `NewDeviceLocalWithDefaults`, open `/dev/net/tun`, `NewIoLoop`,
  set the default route + DNS; browse through a provider from a CLI. Run with
  `sudo`/`setcap` first (snap later). Proves the Android-like data plane on Linux.
- **M1 — snap confinement.** Package as a strict snap with `network-control`;
  confirm the FULL data plane works confined — not just opening the fd but
  installing routes and per-link DNS (R4, the top unknown). Manual `snap connect`
  for now.
- **M2 — GTK4 UI + tray + full auth.** gotk4 + libadwaita window, SNI tray
  (4-state icon + menu), and the FULL auth surface: sign in (email/pw+verify,
  guest, auth-code), **sign up (create network + verify)**, reset password, and
  **Google + Apple via system-browser OAuth** (`urnetwork://` callback via the
  portal). gotk4 stability soak (R1) — decide Go vs gtkmm fallback here.
- **M3 — full feature parity (connect + provide + account).** ALL connect
  controls: the location/provider picker (REST `findLocations`/provider lists +
  the `ConnectGrid`), connect/best-available/selected-location, and the detail
  sheets (contracts, in-tunnel split/block rules, DNS, throughput). **PROVIDE**:
  provide toggle + control mode (never/always/auto/manual) + network mode via
  `ProvideViewController` (in-process DeviceLocal provides directly — simplest of
  the three platforms). Account/Wallet (connect wallet, payout, balance codes,
  reliability, points) + Stripe upgrade, Leaderboard, Support, settings, blocked
  locations, `urnetwork://` OAuth via portal, notifications, autostart, light/dark.
- **M3.5 — split tunneling.** cgroup v2 + SO_MARK/nftables (Mullvad-style),
  including whether it works inside strict confinement (R6).
- **M4 — Snap Store submission.** amd64+arm64, core22/core24, request the
  `network-control` auto-connect exception; privacy disclosure.

## 5. Risks

- **R1 — RESOLVED 2026-07-10 by choosing C++/gtkmm over gotk4.** gotk4's
  documented memory leaks/crashes made it unsuitable for a multi-day tray
  process; the UI is now C++ (gtkmm4 + libadwaita) via the mature GTK stack and
  the cgo wrapper. The residual risk moves to standard C++/gtkmm ergonomics +
  the libadwaita-from-C++ (C API) approach — low, well-trodden.
- **R2 — tray depends on the AppIndicator extension**: default on Ubuntu, not
  vanilla GNOME; manual enable needs logout/login. Acceptable for the Ubuntu/Snap
  target; document for other distros.
- **R3 — snap network-control does not auto-connect**: need a store-review
  auto-connect grant or users run `snap connect`. Request at submission.
- **R4 — full data plane inside strict confinement is UNVERIFIED** [unverified]:
  network-control demonstrably grants the tun fd + CAP_NET_ADMIN, but no evidence
  confirms that *setting the default route and per-link DNS via systemd-resolved*
  also works confined, nor that any shipping single-process VPN snap runs its
  data plane this way (Proton may still fork a confined helper). **Prototype in
  M1 before committing to snap-only.** Biggest architectural risk.
- **R5 — DNS via systemd-resolved inside a snap** [unverified]: per-link DNS +
  DoH via resolvectl/D-Bus (22.04 has resolved; DoH differs 22.04 vs 24.04);
  whether the snap can drive it, or must write `/etc/resolv.conf`, is unverified.
- **R6 — split tunneling inside a snap** [unverified]: cgroup v2 + nftables/
  SO_MARK or net_cls; whether any works under strict confinement is unknown.
- **R7 — desktop integration inside a snap** [unverified]: `urnetwork://`
  deep-link/OAuth via xdg-mime/portal, autostart, notifications, libadwaita
  theming — all need confirmation confined.

## 7. SDK reuse

- **No SDK changes needed for the data plane**: `IoLoop` is already `!windows`
  and fd-based (Android's path); the sdk package builds for linux. The app calls
  the exported Go API directly (like Android's gomobile surface, but in-process
  Go rather than JNI).
- The Linux app IS a C++ consumer of the cgo `.so` + `urnetwork_sdk.hpp` (same
  wrapper as Windows), so `run.sh` building `URnetworkSdkLinux.zip` is now load-
  bearing for the app (not just a third-party artifact). The wrapper exposes the
  unix-only `IoLoop` for the fd data plane. SDK-host logic is shared C++ with the
  Windows app; only the UI toolkit + tun/network layer differ per platform.
- Reuse the generated tray icon art (`windows/app/tools/make-icons.py` source →
  PNG for SNI; SNI takes themed PNG/named icons rather than .ico).
- Egress self-exclusion (R1 on Windows) is **not needed**: single-process on
  Linux, and the SDK's own sockets are the app's — Android handles this via
  `VpnService.protect`; on Linux inside the tunnel we exclude the app's sockets
  by SO_MARK / cgroup (same mechanism as split tunnel, R6) or by binding to the
  physical interface. Track with R6.
